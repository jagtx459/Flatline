Add action target

A target is one machine or service, plus exactly what runs on it when a Flatline group triggers. The type decides how Flatline reaches it.

Credentials are encrypted at rest and never sent back to the browser. When editing, leave a credential blank to keep the stored value.

Set up a Linux account for this

Create a dedicated user that can run the shutdown command without a password prompt (so nothing privileged needs storing here). Run as root / with sudo on the target machine:

sudo useradd -m -s /bin/bash flatline
sudo passwd flatline               # set a password, or use an SSH key instead

# Let it run shutdown without a sudo password:
echo 'flatline ALL=(root) NOPASSWD: /sbin/shutdown, /usr/sbin/shutdown' \
  | sudo tee /etc/sudoers.d/flatline
sudo chmod 440 /etc/sudoers.d/flatline

# (recommended) add your Flatline SSH public key to
# /home/flatline/.ssh/authorized_keys  — chmod 700 the .ssh dir, 600 the file

Then set Username flatline and command sudo shutdown -h +0.

Set up a Windows account for this

Recommended: create a dedicated local admin account rather than using a Microsoft account (whose identity over WinRM/NTLM is unreliable). Run in an elevated PowerShell on the target machine:

net user flatline * /add                     # create the user (prompts for a password)
net localgroup Administrators flatline /add  # WinRM requires admin rights
Enable-PSRemoting -Force                     # turn on WinRM / PowerShell remoting

# Workgroup (non-domain) machines only: let local accounts sign in remotely
# with full rights, otherwise you get "Access is denied":
New-ItemProperty -Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System' `
  -Name LocalAccountTokenFilterPolicy -Value 1 -PropertyType DWord -Force
Restart-Service WinRM

Then set Username flatline, leave Domain blank, and keep port 5985.

To use HTTPS instead, do the above first, then add a certificate and an HTTPS listener. Enable-PSRemoting sets up the HTTP listener on 5985 only — nothing listens on 5986 until step 2 below, and Flatline cannot set it up for you:

# 1. A certificate in LocalMachine\My. $dns must be the name Flatline
#    connects to. Already have one (a domain CA cert, say)? Skip this and
#    set $c with: $c = Get-Item Cert:\LocalMachine\My\<thumbprint>
$dns = 'win-host.example.com'
$c = New-SelfSignedCertificate -DnsName $dns -CertStoreLocation Cert:\LocalMachine\My

# 2. The HTTPS listener — this is what puts WinRM on 5986. Any existing one
#    is removed first, so re-running this is safe.
Get-ChildItem WSMan:\localhost\Listener |
  Where-Object { $_.Keys -contains 'Transport=HTTPS' } | Remove-Item -Recurse -Force
New-Item -Path WSMan:\localhost\Listener -Transport HTTPS -Address * `
  -HostName $dns -CertificateThumbPrint $c.Thumbprint -Force

# 3. Open the port. Enable-PSRemoting opened 5985, not this one.
New-NetFirewallRule -DisplayName 'WinRM HTTPS' -Direction Inbound `
  -LocalPort 5986 -Protocol TCP -Action Allow

# 4. Confirm it took — you should see a Transport=HTTPS listener, Enabled=true.
winrm enumerate winrm/config/Listener

# 5. Optional: print the certificate as PEM, to paste into CA certificate
#    below so Flatline verifies against it instead of trusting blindly.
"-----BEGIN CERTIFICATE-----"
[Convert]::ToBase64String($c.RawData, 'InsertLineBreaks')
"-----END CERTIFICATE-----"

Then tick Use HTTPS below and set Host to the name on the certificate ($dns) — an IP address will fail verification unless the certificate names it too. A self-signed certificate needs either its PEM in CA certificate, or Accept untrusted certificate.

Off (default): plain WinRM on 5985. The connection is still encrypted — the SOAP body is sealed with the NTLM session key — and it works against a stock Enable-PSRemoting host with nothing else to set up.

On: WinRM over TLS on 5986. Needs an HTTPS listener and a certificate on the host (see the setup notes above). Sign-in is still NTLM; TLS replaces the NTLM sealing and authenticates the host to Flatline.
2-step auth

For an API that will not accept a static key: Flatline signs in first, reads a token out of that response, and sends it on the real request.

This happens fresh every time, including on restore — a token minted during the outage would have expired by the time the service is back.

Worked examples

Two common shapes. Yours may differ — check what your API's login endpoint actually returns, with curl -i, and fill in the fields to match.

Token in the response body, and a session cookie you have to build yourself (Proxmox VE):

Login URL      https://host:8006/api2/json/access/ticket
Credentials    in the request body, form-encoded
Login body     username={username}&password={password}
Username       root@pam
Token from     the response body, at  data.CSRFPreventionToken
Send token in  CSRFPreventionToken
Cookie name    PVEAuthCookie
Cookie value   from the response body, at  data.ticket

Token in a response header, session cookie set for you (UniFi OS):

Login URL      https://host/api/auth/login
Credentials    in the request body, JSON
Login body     {"username":"{username}","password":"{password}"}
Token from     the response header  X-CSRF-Token
Send token in  X-CSRF-Token
Cookies        leave "send login cookies" ticked

A CSRF token is usually only accepted alongside the session it was minted for. Leave this on unless you know the service sets no cookies — it is harmless when it doesn't.

The two fields below are only needed when the service returns its session in the response body and expects the client to assemble the cookie itself, never sending a Set-Cookie of its own. Fill in both or neither.

Only applies to https:// URLs.

The same service can need this or not depending on how you reach it: through a reverse proxy on a real hostname the certificate is trusted, but on a bare IP it is usually the appliance's own self-signed one.

Ticking this stops Flatline checking who it is talking to, so prefer supplying the CA below where you can.
▸ Restore

What Flatline does to bring this target back after its trigger action ran, in three steps: 1. the restore itself, 2. the wait for it to answer, 3. an optional action once it is up.

Both methods are yours to pick and are independent of how the target itself is reached — a cluster taken down over its API can be woken with a magic packet and finished off over SSH.

There is no snapshot of prior state anywhere. A restore is only as good as what you configure here — Flatline does not record which nodes were cordoned or what a shutdown command turned off.

The target's Restore button runs this on demand, whether or not auto-restore is on.

Runs on its own once the Flatline group that triggered the shutdown reports healthy again.

Targets restore in the reverse of the order they were shut down in, so only the ones ticked here come back automatically.
1

Makes the nodes schedulable again — the mirror image of a cordon + drain. Nothing records which nodes were cordoned before the outage, so every node in the cluster is uncordoned.

Scaling workloads back up achieves nothing while the nodes are unschedulable, so leave this on unless something else manages the cordons.

The same thing as kubectl rollout restart deployment, in every namespace except kube-system (CoreDNS and the control-plane addons come back on their own).

Evicted pods reschedule without this once nodes are schedulable again — it's for the ones that come back wedged, e.g. a half-finished rollout or a CrashLoopBackOff against a dependency that was itself down.
2
Wait up to seconds, then give up.

A give-up budget, not a sleep: Flatline polls every 10s and moves on the moment whatever it is waiting for answers. 0 means one attempt.

It is spent wherever the sequence actually has to wait — for a booted host before step 3's command, or for the API server before a Kubernetes restore can uncordon anything. Nothing runs until that answers.

Auto-restore starts the moment the Flatline group reports healthy, which is usually before a booting host or a cluster's control plane is ready.

The HTTP method is the exception: its static auth schemes have no request that is safe to repeat, so they send once and ignore this. Only a 2-step-auth target has a safe probe — its login — to wait on.
3

Makes the nodes schedulable again — the mirror image of a cordon + drain. Nothing records which nodes were cordoned before the outage, so every node in the cluster is uncordoned.

The same thing as kubectl rollout restart deployment, in every namespace except kube-system.

Add action group

An action group is an ordered list of stages. On trigger the stages run top to bottom; the targets within a stage run simultaneously, until a wait splits it — then what is below the wait starts once it is up.

Flatline groups are managed on the Flatline page.

Stops a run the moment the Flatline group that triggered it is back — the stages below it answer an outage that is over. Restored means no longer down by that group's own rule, all or any: the same rule that triggered this.

It takes hold between stages. A stage already running finishes, since its commands are already on their way to remote hosts.

The targets it did run are then brought back, each following its own restore and auto-restore settings. The ones it never reached are left alone.

A run started by hand has no group to watch, so this does not apply to it.
